# ADR-001: Split the agent into node and controller roles

Status: accepted, 2026-10-08 (owner decision on ISS-058, option A)
Plan: PLAN-002 11.1

## Context

The agent runs as one DaemonSet. Every pod does three different jobs:

1. Watch the pods on its own node and act on them (crashloop, OOM, image
   pull, node pressure). This must stay per node (CLAUDE.md constraint 3).
2. Run the cluster-wide loops (jobs, rollouts, HPAs, PDBs, Prometheus
   checks, finalizers, unschedulable pods). Only the leader does this.
3. Serve the dashboard, the HTTP API and the Slack callback.

Mixing the three causes real defects:

- ISS-047: each pod keeps its own event log. The Service spreads dashboard
  requests across all pods, so every refresh can show a different node, and
  findings from the leader loops appear only when a request lands on the
  leader.
- ISS-043: a pod that is not yet on a node was invisible to every node agent
  (fixed by moving the check to the leader, which this ADR makes the rule).
- Every node pod runs cluster-wide informers and client limits, so API
  server load grows with the node count.
- ISS-055: every pod announces start and stop on Slack.

## Decision

One binary and one image, two roles chosen by `AGENT_ROLE`:

| | `node` | `controller` |
| --- | --- | --- |
| Workload | DaemonSet, one pod per node | Deployment, two replicas |
| Watches | pods on its own node, its own Node | everything in the allowlist |
| Acts on | its own node and the pods on it, through the mutation gate | workloads, through the mutation gate, leader only |
| Leader election | none | yes, the existing Lease; the leader runs the cluster loops |
| Event log | none of its own; every event is forwarded to the controller | the one event log, persisted |
| HTTP | `/healthz`, `/readyz`, `/metrics` only | dashboard, `/api/*`, Slack callback, internal ingest |
| Slack | incident messages for its own node | incident messages for cluster findings; the only start and stop notice |

`AGENT_ROLE=all` keeps today's single-process behaviour for local runs and
tests. The chart deploys `node` plus `controller`; `all` is not a supported
production mode.

### How node findings reach the controller

- The node agent records events through an `events.Sink` interface. In the
  `node` role the sink is a forwarder that POSTs batches to the controller
  Service at `/internal/v1/events`, with a bounded in-memory buffer and
  retry; when the buffer is full the oldest events are dropped and counted
  (`auto_agent_events_dropped_total`), never blocking a handler.
- The endpoint takes a shared token from a Secret key (`internal-token`),
  generated by the chart, separate from the dashboard token. Requests
  without it are refused (constraint 9). Payloads pass through redaction on
  the controller before storage, as every outbound path already does on
  the node (constraint 8).
- Audit records travel the same way, so the controller holds one audit view.

### One view behind one Service

- The Service selects controller pods only.
- The standby controller proxies `/api/*` to the leader, found through the
  Lease holder identity (its pod name) and the pod's IP. It stays Ready, so
  a leader change needs no endpoint shuffle; during the handover window the
  standby answers 503 with `Retry-After`.

### Permissions follow the split (constraint 7)

Two ServiceAccounts. The node account gets what node handlers use (pods on
its node: get, list, watch, delete, evict; its Node: get, patch; pods/log).
The controller account gets the cluster reads, workload writes and the
Lease. `TestRBAC_ChartMatchesCode` is extended to check each account against
the code its role runs.

## Consequences

- Two workloads to install and upgrade; the chart and the generated
  manifests (11.3) carry both.
- A new internal endpoint to secure and test.
- Node agents no longer need cluster-wide reads, which shrinks their
  permissions and the API load per node.
- The dashboard, the API and Slack speak with one voice.
- The leader copies every event it stores, its own and those ingested from
  node agents, to the standby, so after a leader change the new leader
  already holds the history (ISS-059). A standby that starts later has
  only what was recorded after it joined.
- The rate limiter, circuit breaker and blast radius stay per process: a node
  agent limits actions on its node, the controller limits cluster actions.
  A cluster-wide budget across nodes is not part of this ADR.

## Rejected

- **B, keep the DaemonSet and proxy to the leader.** Node findings would
  still live only on their node's pod unless pushed anyway, and every node
  would keep the cluster-wide informers.
- **C, a shared store (custom resources, ConfigMaps or a database).** Write
  load on etcd for every event, or a new external dependency to run.
